Two different measurements

“Packages it” and “Deploys it” use different clocks

A completed build is not a live deployment. The charts keep these separate.

Packages it: source → complete deployable output

Before the clockInstall local Lambda dependencies and tools; establish the chosen cache state.
→
Clock runsNative package/build command or managed build phase, through completion of its output.
→
After the clockInspect size, verify the actual package/image, and check upload parity outside timing.

Container dependency installation performed by the builder is inside its build time. Managed build scheduling, checkout, upload and service rollout are outside packaging time.

Build seriesWhat happens?
Clean buildRemove the qualified build outputs/caches, then build. Installed local Lambda dependencies and downloaded Docker base images are disclosed separately.
Rebuild after a code editKeep normal build caches, change the source version marker, then build again. Save what the builder actually reused.
Package sizeLambda: compressed function ZIPs plus required shared layers counted once. Containers: complete compressed image bytes. This is not the traffic transferred by a cached incremental push.

The same six app shapes get these deployment journeys: 1, 5 and 25 Lambdas; Node API; Python API; five services. Only supported and verified platform/journey combinations enter a chart.

Our fast deployment path is mandatory

Our CLI uses automatic fast deployment/hotswap. CDK uses hotswap. Serverless updates each changed function. SST uses cloud deployment, not Live mode. The hosted platforms use their fastest supported real-cloud paths.

For our Git pushes, the proposal is native Console CI, including its actual fresh or reused runner and caches. The repository’s GitHub Actions workflow is a fallback. A GitHub Actions result will not be presented as a native warm-runner result. Native CI wiring and observation still need to be finished before timing.

Frameworks run their native commands through GitHub Actions; Render, Ravion and Heroku use their own Git automation. Different builder capacities and rollout guarantees appear beside the results.

What “usual production settings” means

Each tool keeps its normal production packaging behavior: minification, source maps, dependency handling and builder choice. We disclose effective differences rather than silently forcing identical flags that some tools do not support. CDK’s hotswap is documented as a development path with infrastructure drift; its speed does not imply equivalent production rollout guarantees.

What cleanup must include

  1. At creation: save exact resource IDs, ownership, region and the recovery command.
  2. After each paired test batch: destroy owned platform apps/projects and AWS resources, including runners, disks, load balancers/NAT/public IPs and retained artifacts.
  3. After failure or interruption: run the saved cleanup procedure before starting the next batch.
  4. Verify: query the recorded IDs and confirm deletion. A command returning success is insufficient.
  5. At campaign end: disable benchmark CI and remove the temporary Ravion AWS connection.

Stopping a runner is not complete cleanup. Its disks, stored images and other owned resources can keep costing money. The cleanup ledger must cover those resources too, and it must show exact-ID deletion checks.

The complete plan is large, so execute it in stages

Ten samples of every proposed build/cache/deployment combination can mean up to 1,380 attempts, before retries or unsupported cells. The 300 repeat-push attempts contain 75 cumulative application-hours of 15-minute waits. Those are cumulative waits, not a promise of wall-clock duration or a bill estimate.

  1. First prove the method: a small five-Lambda and Node API qualification batch, including Heroku’s Node builder. These are setup checks, not publishable rankings.
  2. Then collect the primary comparison: only after native builders, fast paths and correct live revisions pass. Keep all failures and alternate provider order.
  3. Expand to the full matrix: maintain the declared tests and sample rules while the projected remaining cost fits the $50 cap. If it does not fit, stop, clean up and report the remaining cases before spending more.

Opus supports the matrix and staged execution, but it could not verify a full-campaign price. Each measured row must include every supported competitor in a rotated order. If the row cannot fit the remaining budget plus reserve, stop the whole row, clean up and report it as unrun; do not quietly drop one competitor.
